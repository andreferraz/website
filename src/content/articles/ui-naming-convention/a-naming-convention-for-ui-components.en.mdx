Naming things in software development has always had its challenges. Even today with AI taking a lot of this responsibility, a good naming pattern can help us maintain consistency and clarity in our codebase.

In 2021, I published an [article on Medium](https://andreferrazdev.medium.com/a-naming-convention-for-ui-components-77f4fb8797c) explaining the naming pattern that my team and I were using. That article got quite popular, so I wanted to bring it here as well, but now with revised rules, some updates, and more examples.

This is an updated documentation for the **<abbr title="Context, Element, Variant">CEV</abbr>** naming pattern, a **simple** and **intuitive** naming convention for UI components.

## The CEV pattern

CEV stands for **<span className="text-fg-red">Context</span>**, **<span className="text-fg-blue">Element</span>** and **<span className="text-fg-green">Variant</span>**.

We call each of these a **token** of the component's name (_do not confuse with LLM tokens_ 😉).

| Token | Description | Examples |
| --- | --- | --- |
| **<span className="text-fg-red">Context</span>** | The domain or feature the component belongs to | `Auth`, `Cart`, `Article`, `App` |
| **<span className="text-fg-blue">Element</span>** | The concrete UI piece(s) | `Button`, `Card`, `Input`, `Links` |
| **<span className="text-fg-green">Variant</span>** | An optional modifier that differentiates similar components | `Featured`, `Compact`, `Stacked`, `Inverted` |

### Examples

Here is a short list of examples to better illustrate it.

| Component | Notes |
| --- | --- |
| <span className="text-fg-red">Product</span> <span className="text-fg-blue">Card</span> | Most common case: singular context and element, no variant. |
| <span className="text-fg-red">Product</span> <span className="text-fg-blue">Card</span> <span className="text-fg-green">Compact</span> | Same as the above, but with a size/format variant. |
| <span className="text-fg-red">Members</span> <span className="text-fg-blue">List</span> | Plural context with singular element, no variant. |
| <span className="text-fg-red">Footer</span> <span className="text-fg-blue">Links</span> | Singular context and plural element, no variant. |
| <span className="text-fg-red">Text</span> <span className="text-fg-blue">Blocks</span> <span className="text-fg-green">Stacked</span> | Layout variant that helps understand the structure. |
| <span className="text-fg-red">Flexible</span> <span className="text-fg-blue">Content</span> | Broader context. |

## Specifications

Just with the examples above you may already have a good sense of the pattern. But if you want to use it, you may need some more specific rules to adopt it in your projects or team.

Here is a breakdown for each token usage.

### <span className="text-fg-red">Context</span>

The context can be the name of a parent element or page where this belongs, the type of content that will be instantiated, or anything that helps you understand what the scope of this component is.

**Question answered:**

What scope or behavior does this component belong to or respect?

**Typical forms:**

- Singular noun: `Article`, `Product`, `Member`, `Site`, `Checkout`
- Plural noun (for collection-oriented elements): `Articles`, `Products`, `Questions`, `Users`, `Comments`
- Occasional adjective-like context when it denotes behavior: `Flexible`, `Collapsible`, `Modular`

**Naming rules:**

- Context **<span className="uppercase">should</span>** describe business or content domain scope.
- Context **<span className="uppercase">may</span>** describe behavior when behavior defines the component's functional role.
- Context **<span className="uppercase">should</span>** be plural when the component scope is collection-oriented.
- Context **<span className="uppercase">should not</span>** encode purely visual style.

### <span className="text-fg-blue">Element</span>

The element name should make clear what to expect from this component in the UI.

**Question answered**:

What type of UI element is it?

**Typical forms:**

- Singular noun: `List`, `Card`, `Form`, `Section`, `Block`, `Carousel`, `Accordion`, `Hero`, `Menu`, `Field`
- Plural noun (when the element represents a grouped set): `Tabs`, `Steps`, `Links`, `Fields`, `Buttons`

**Naming rules:**

- Element **<span className="uppercase">must</span>** describe UI role or structure.
- Element **<span className="uppercase">should</span>** be specific enough for search.
- Element **<span className="uppercase">should</span>** be plural when it represents a grouped set.
- Element **<span className="uppercase">must not</span>** be a vague placeholder like `Thing`, `Component`, `Object` unless that is a real domain term.

### <span className="text-fg-green">Variant</span>

The variant is optional and should be used when the variation is significant enough to be worth a separate component, but you still want it to be close to its siblings.

**Question answered**:

Is this a meaningful variation of a base component?

**Typical forms:**

- Size adjective: `Compact`, `Large`
- Emphasis or prominence adjective: `Featured`, `Highlighted`
- Layout or orientation adjective: `Stacked`, `Inverted`
- Capability or complexity adjective: `Advanced`, `Minimal`

**Naming rules:**

- Variant **<span className="uppercase">may</span>** be used when an existing component does not suffice.
- Variant **<span className="uppercase">must</span>** come after `Element`.
- Variant **<span className="uppercase">should not</span>** be used for temporary implementation details.
- Variant **<span className="uppercase">should not</span>** be a noun, since it can be confused with an element.

## Edge cases

Although the rules above may work for most cases, I've been working with this pattern for time enough to know that we might want a bit of flexibility here and there.

Whether or not to follow these depends on your team and project context.

### Omitting <span className="text-fg-red">context</span>

In some cases, the component may be obvious or commonly global, and requiring only the <span className="text-fg-blue">element</span> name may be enough.

**Examples**:

- `Header`
- `Footer`
- `Sidebar`

**Recommendation**:

- **<span className="uppercase">allowed</span>** when the element is used once across the app and its meaning is clear.
- **<span className="uppercase">discouraged</span>** in large monorepos where names can become unclear.

Teams may prefer to use a stricter rule that always requires <span className="text-fg-red">context</span> to **avoid ambiguity**, always adding context like in `SiteHeader`, `AppFooter` or `LayoutSidebar`.

### Multi-word tokens

Sometimes one word is too broad. In those cases, a multi-word token can make the component name clearer and easier to find.

**Examples**:

- `ArticleFaqAccordion`: `FaqAccordion` may be too broad in a large codebase.
- `OrderHistoryTable`: `HistoryTable` can become too generic outside order-related features.
- `UserProfileForm`: `ProfileForm` may conflict with team, organization, or company profile flows.

Multi-word tokens may be more common in the <span className="text-fg-red">context</span>, but they can also be the <span className="text-fg-blue">element</span> or even the <span className="text-fg-green">variant</span>.

Alternatively, multi-word tokens can be fully avoided with grouping or nesting components if your project structure allows it, like `Article/FaqAccordion`, `Order/HistoryTable` or `User/ProfileForm`.

Deciding whether to use it depends on your project structure and team preferences.

**Recommendation**:

- **<span className="uppercase">allowed</span>** when improving meaning, when a single word would hide important domain meaning.
- **<span className="uppercase">discouraged</span>** when a single word may be enough, and the extra words do not add valuable context.

## Final notes

A naming pattern should exist to help, not to make it harder. If a rule adds more friction than value in your context, adapt it. What matters the most is that your project (and maybe team) uses a consistent and understandable convention.

There's no one-size-fits-all solution with naming conventions. The goal with the CEV pattern is to make components easy to **find**, **sort**, and **understand** from the name alone.
